# Production V2 replay architecture assessment

Source checked on `productionv2` after the shared Inventory candidate extraction.

1. **Shared architecture.** `StockReplayPhysicalTimelineReader`, `StockReplayPhysicalSimulator`, `StockReplayPhysicalPlanner` and `StockReplayPhysicalAsOfReader` already read, rewind, project and revalidate exact `IvBalLoc` piles. WAC, FIFO and Standard each have shared financial readers, simulators, planners and reconciliation writers. `StockPostingCoordinator` owns the sealed root transaction.
2. **Repeated physical orchestration.** The MR, MI/Scrap and transfer paths in `IvInventoryPostingService.*Replay.cs` repeat draft selection, a provisional event key, physical candidate construction, tail checks, root revalidation and completion. `IvStockCountService.Replay.cs` has the distinct absolute-count orchestration. The provisional ordinary Inventory candidate is now centralized in `StockReplayInventoryCandidatePlanner`; the other stages remain separate where their authority differs.
3. **Repeated cost orchestration.** WAC, FIFO and Standard posting paths each select an item-wide tail and coordinate its method-specific writer. The cost algorithms themselves already live in shared `StockReplay*` services; there is no reason to replace them with one method-neutral cost calculator.
4. **Sales shipment.** DO and Invoice already use `IvSpShipmentService` and `IvSpShipmentAllocator`. Invoice excludes `LinkDo` lines from its direct shipment request. Their service-level lifecycle, confirmation and DTO mapping are similar but document-owned. Audit remaining duplication before extracting another Sales component.
5. **Production.** `ProductionReplayDependencyPlanner`, `ProductionPoolValuationService` and active contribution/correction readers provide shared parts. `ProductionFinishedGoodReceiptService.CostTrace` also replays a WIP pool. WIP contribution and conversion-cost lineage are different from Inventory pile quantity, so reuse the planning and authority contracts where possible without forcing a single ledger model.
6. **Safe consolidation.** Use a normalized physical candidate for ordinary Inventory IN, OUT and paired transfer legs, then pass the resulting immutable plans to existing cost-method writers. Share an owner/tail validation component only after its exact supported descendant set is specified. Keep the count reset path and cross-module value propagation distinct.
7. **Document-specific contracts.** MR receipt price authority, Scrap movement/reason, Vendor Return PO return quantity, GR receipt/settlement, transfer equal-value legs, DO versus direct-Invoice stock ownership, Production WIP/contribution lineage and FG valuation remain in adapters and downstream hooks.
8. **Tests.** Keep deep physical and cost tests in `StockReplayPhysicalSimulatorTests`, `StockReplayWacSimulatorTests`, `StockReplayFifoLayerAllocatorTests` and `StockReplayStandardSimulatorTests`. Keep focused public post/rollback tests for each document's owner, side effects, fail-closed behavior and atomicity. Do not delete existing integration tests solely because a shared helper is introduced.
9. **Refactor risk and files.** The candidate extraction changes `StockReplayInventoryCandidatePlanner.cs` plus `IvInventoryPostingService.{WacReplay,FifoReplay,StandardMrReplay,StandardMiReplay,WacTransferPostReplay,FifoTransferReplay,StandardTransferReplay}.cs`. `StockReplayInventoryReceiptPileLocator.cs` now selects the one existing MR destination pile for all three cost methods; the receipt authority still rechecks exact item, lot, expiry, active warehouse/location/status and price evidence under the root lock. Bounded lot support adds `StockReplayInventoryIssuePileAuthority.cs` and changes the WAC/FIFO issue post and rollback writers, their candidate/value checks, `IvInventoryPostingService.{WacReplay,StandardMiReplay}.cs`, and `IvMiscIssueLedgerAuthorityTests.cs`. A larger rewrite could change event ordering, stale-plan detection, lot authority or sealed valuation lineage. The candidate helper constructs read-only plans; root-lock validation and method-specific cost writers remain authoritative. The adjacent Inventory selection passes 128/128.
10. **Next step.** The bounded WAC, FIFO and Standard MI/Scrap routes accept an existing lot-controlled source pile after exact pile/lot validation under the root lock. Public MI and Scrap post/rollback cases for all three methods prove lot identity and historical availability despite a later live `TransDate`; FIFO retains an item-wide financial pool and records lot provenance on each split. A public WAC case rejects an 8-unit issue before a later 10-unit lot receipt when historical stock was only 5, then posts and rolls back a valid 4-unit issue. The bounded WAC, Standard and FIFO MR routes accept a receipt into one existing active lot pile, retain its lot identity on history and value, and reject a tampered lot before rollback. WAC and FIFO recost later issues; Standard uses its effective date revision. A lot-controlled transfer creates a new destination lot under the ordinary document contract, so all three backdated transfer routes explicitly reject that unsupported creation before mutation. New-lot/pile replay needs virtual physical planning and atomic lot creation. Cross-module descendant, SQL Server concurrency and full rollout certification remain separate gates; migration is deferred for this development pass.

For an ordinary historical insertion, the final live quantity must reconcile to the signed change after replaying later movements. A later absolute count can absorb that change. It is not an invariant that every historical insertion leaves the live quantity unchanged.

The WAC Inventory issue route now also covers one backdated Vendor Return. It uses the shared historical physical candidate and WAC issue cost writer, then applies the PO return quantity in the same branch-locked transaction. Its original history records PO line and purchase quantity so rollback can verify the document has not changed before reversing stock and PO together. Standard Vendor Return reuses the bounded Standard MI projection, checks immutable PO identity on rollback, and updates PO ReturnQty inside the replay transaction. FIFO Vendor Return now uses the bounded FIFO issue root for one existing pile with later Inventory MI/Scrap descendants; it records PO lineage on ordinary and replay origins and updates ReturnQty atomically. A two-layer case proves later MI repricing and restoration after rollback; the adjacent Vendor Return, issue and receipt selection passes 107/107. Older ordinary VR origins lacking PO history fail closed under historical rollback. The public atomicity and tamper case passes, and the neighboring inventory selection passes 72/72.

Inventory POST routing now has a shared read-only dependency decision before legacy stock-date checks. `StockReplayInventoryRouteSelector` combines exact active later pile events, unreversed later valuation and a newer live pile date; it resolves one existing receipt destination pile when the draft has not stored its ID. The live date is only a conservative signal: method-specific physical and financial planners remain responsible for proving that stock existed and was sufficient at the candidate date. A historical dependency with no accepted bounded route returns an explicit unsupported result before ordinary posting; the ordinary path rechecks under the branch lock and returns a retryable staleness result if chronology changed. Flag OFF still uses the previous path. MR, MI/Scrap, Vendor Return, transfer, GR and standalone adjustment use the decision; count-owned adjustments retain their own route. The latest adjacent Inventory selection passes 172/172 and the adjustment/count selection passes 188/188. Local ERPWeb inspection found Batch 12 was a 6 October WAC MR before a sealed 14 October MR; enabling Development replay and restarting the debug app allowed two post/rollback cycles, with original/reversal valuation lineage and final 100-unit/250-value state confirmed read-only.

Rollback uses the same selector with the posted document's active original history and original posting key. It checks for later active physical and valuation effects after each method-specific replay attempt, and it rechecks the fast path under the branch lock. It does not use the live pile date as rollback authority. An unsupported historical rollback now stops before ordinary reversal; count-owned adjustment still belongs to the Stock Count route. A WAC Vendor Return lifecycle proves that a later MI already reversed leaves only audit evidence and does not block the return rollback. The combined adjacent Inventory, adjustment and count selection passes 361/361.

Goods Receipt rollback verifies each saved posted line against its active original history before PO write-back. A bounded WAC GR historical route handles one stock line into an existing pile before supported later Inventory events. Its separate GR authority checks the frozen provisional PO unit cost, approved transaction-date currency rate, item/pile identity and uninvoiced PO line; the shared WAC receipt writer records GR ownership while the root transaction updates PO RecvQty, stock and valuation together. A foreign-currency case rejects a changed rate without stock/PO mutation, then posts and rolls back at the approved rate. Historical rollback checks the original PO identity and rejects invoice settlement before reversing PO quantity, receipt value and later Inventory repricing. The WAC tail also accepts a later sealed GR receipt with unchanged fixed cost and no settlement, then reprices following Inventory issues; a case proves the earlier GR post/rollback retains the later GR's PO quantity and valuation. A settlement, invoiced quantity or unresolved PO line on the later GR blocks replay. The bounded Standard GR route now uses the existing Standard MR physical and financial plan for one existing pile, but substitutes the GR's approved PO/currency authority, writes GR history at the effective Standard revision, and updates PO RecvQty in the same root. Its rollback checks exact posted GR identity, invoice settlement and PO capacity before removing the Standard value and PO quantity. A public case with a later MI proves 16 units/104 value and PO quantity 5 after post, then 11 units/71.5 value and PO quantity zero after rollback; altered draft cost and invoiced PO quantity reject without mutation. The Goods Receipt suite passes 36/36 and the adjacent Standard MR lifecycle passes. The bounded FIFO GR route shares the FIFO MR layer plan with GR-specific PO/base-cost authority and PO quantity write-back; a public later-MI lifecycle, repost and second rollback pass with exact layer and issue-value restoration. The Standard tail now also accepts a later sealed GR only when its exact PO line is uninvoiced and has no receipt settlement; an earlier Standard GR post and rollback preserve that later GR valuation and PO quantity, while invoice quantity or settlement evidence blocks repost. The FIFO tail likewise accepts a later sealed GR only with exact receipt/fact/PO lineage, zero invoiced quantity and no settlement; a later MI is repriced while the GR layer and PO quantity stay fixed, and rollback restores the prior FIFO pool. New piles, later invoiced GR or cross-module descendants, and late GR before PI settlement still need their own routes; the replay flag remains OFF by default.

The PI settlement allocator now has a replay-root parameter for the one unsealed GR receipt belonging to its current root. Without that parameter, ordinary PI allocation still reads sealed receipts only. With it, the allocator verifies the same live GR root, transaction and tenant, then admits only that root's unsealed valuation fact; another unsealed GR remains invisible. A focused two-GR SQLite case proves the exclusion and the exact own-root allocation. PI rollback now selects active settlement and purchase-adjustment roots after older roots have reversal children, so a later replacement can be reversed without resurrecting the original. This is prerequisite lineage handling for late-GR settlement replay, not a completed PI remap: the remap writer, CN generation handling and downstream WAC/FIFO value propagation must still be completed before the GR route may accept an already invoiced PO line.

The active PI rollback generation also verifies that every live settlement slice has a matching live purchase-cost adjustment by invoice/PO line, base quantity and actual amount. Both root queries use database snapshots so a tracked stale entity cannot hide a changed adjustment. Focused missing and mismatched adjustment cases fail before appending reversals; repaired active replacement roots still reverse successfully. GR descendant checks also bind later Standard/FIFO receipt valuations to their original GR source and FIFO posting order. Goods Receipt and PI selection passes 51/51; the full PI remap and dependent CN/cost propagation remain the next implementation gate.
