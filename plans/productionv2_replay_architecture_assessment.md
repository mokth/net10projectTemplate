# Production V2 replay architecture assessment

Source checked on `productionv2` after the shared Inventory candidate extraction.

1. **Shared architecture.** `StockReplayPhysicalTimelineReader`, `StockReplayPhysicalSimulator`, `StockReplayPhysicalPlanner` and `StockReplayPhysicalAsOfReader` already read, rewind, project and revalidate exact `IvBalLoc` piles. WAC, FIFO and Standard each have shared financial readers, simulators, planners and reconciliation writers. `StockPostingCoordinator` owns the sealed root transaction.
2. **Repeated physical orchestration.** The MR, MI/Scrap and transfer paths in `IvInventoryPostingService.*Replay.cs` repeat draft selection, a provisional event key, physical candidate construction, tail checks, root revalidation and completion. `IvStockCountService.Replay.cs` has the distinct absolute-count orchestration. The provisional ordinary Inventory candidate is now centralized in `StockReplayInventoryCandidatePlanner`; the other stages remain separate where their authority differs.
3. **Repeated cost orchestration.** WAC, FIFO and Standard posting paths each select an item-wide tail and coordinate its method-specific writer. The cost algorithms themselves already live in shared `StockReplay*` services; there is no reason to replace them with one method-neutral cost calculator.
4. **Sales shipment.** DO and Invoice already use `IvSpShipmentService` and `IvSpShipmentAllocator`. Invoice excludes `LinkDo` lines from its direct shipment request. Their service-level lifecycle, confirmation and DTO mapping are similar but document-owned. Audit remaining duplication before extracting another Sales component.
5. **Production.** `ProductionReplayDependencyPlanner`, `ProductionPoolValuationService` and active contribution/correction readers provide shared parts. `ProductionFinishedGoodReceiptService.CostTrace` also replays a WIP pool. WIP contribution and conversion-cost lineage are different from Inventory pile quantity, so reuse the planning and authority contracts where possible without forcing a single ledger model.
6. **Safe consolidation.** Use a normalized physical candidate for ordinary Inventory IN, OUT and paired transfer legs, then pass the resulting immutable plans to existing cost-method writers. Share an owner/tail validation component only after its exact supported descendant set is specified. Keep the count reset path and cross-module value propagation distinct.
7. **Document-specific contracts.** MR receipt price authority, Scrap movement/reason, Vendor Return PO return quantity, GR receipt/settlement, transfer equal-value legs, DO versus direct-Invoice stock ownership, Production WIP/contribution lineage and FG valuation remain in adapters and downstream hooks.
8. **Tests.** Keep deep physical and cost tests in `StockReplayPhysicalSimulatorTests`, `StockReplayWacSimulatorTests`, `StockReplayFifoLayerAllocatorTests` and `StockReplayStandardSimulatorTests`. Keep focused public post/rollback tests for each document's owner, side effects, fail-closed behavior and atomicity. Do not delete existing integration tests solely because a shared helper is introduced.
9. **Refactor risk and files.** The candidate extraction changes `StockReplayInventoryCandidatePlanner.cs` plus `IvInventoryPostingService.{WacReplay,FifoReplay,StandardMrReplay,StandardMiReplay,WacTransferPostReplay,FifoTransferReplay,StandardTransferReplay}.cs`. `StockReplayInventoryReceiptPileLocator.cs` now selects the one existing MR destination pile for all three cost methods; the receipt authority still rechecks exact item, lot, expiry, active warehouse/location/status and price evidence under the root lock. Bounded lot support adds `StockReplayInventoryIssuePileAuthority.cs` and changes the WAC/FIFO issue post and rollback writers, their candidate/value checks, `IvInventoryPostingService.{WacReplay,StandardMiReplay}.cs`, and `IvMiscIssueLedgerAuthorityTests.cs`. A larger rewrite could change event ordering, stale-plan detection, lot authority or sealed valuation lineage. The candidate helper constructs read-only plans; root-lock validation and method-specific cost writers remain authoritative. The adjacent Inventory selection passes 128/128.
10. **Next step.** The bounded WAC, FIFO and Standard MI/Scrap routes accept an existing lot-controlled source pile after exact pile/lot validation under the root lock. Public MI and Scrap post/rollback cases for all three methods prove lot identity and historical availability despite a later live `TransDate`; FIFO retains an item-wide financial pool and records lot provenance on each split. A public WAC case rejects an 8-unit issue before a later 10-unit lot receipt when historical stock was only 5, then posts and rolls back a valid 4-unit issue. The bounded WAC, Standard and FIFO MR routes accept a receipt into one existing active lot pile, retain its lot identity on history and value, and reject a tampered lot before rollback. WAC and FIFO recost later issues; Standard uses its effective date revision. A lot-controlled transfer creates a new destination lot under the ordinary document contract, so all three backdated transfer routes explicitly reject that unsupported creation before mutation. New-lot/pile replay needs virtual physical planning and atomic lot creation. Cross-module descendant, SQL Server concurrency and full rollout certification remain separate gates; migration is deferred for this development pass.

For an ordinary historical insertion, the final live quantity must reconcile to the signed change after replaying later movements. A later absolute count can absorb that change. It is not an invariant that every historical insertion leaves the live quantity unchanged.
