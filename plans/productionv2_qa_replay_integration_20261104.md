- Source: `productionv2` at `ed703f6665d90cc979043395afd3089ec36fdd86` with the uncommitted replay work described in `productionv2_wac_fg_replay_scope_20261104.md`. - Scope: combine the existing QA module and its receipt, stock-hold, production-hold and finished-good authorization calls with the current bounded replay implementation. Do not enable replay or change the user's database. The user explicitly does not need a migration.
- Public routes to trace: MR and GR post/rollback including WAC/FIFO/Standard replay; MI and transfer post/rollback with physical QA holds; Production material issue, Daily Production and finished-good post/rollback with logical holds and receipt grants. QA grant/hold changes must use the same root transaction as the corresponding stock change, including on failure and retry.
- Count replay also writes projected pile quantities directly instead of using the ordinary Inventory adjustment route. Check each affected pile's projected final quantity against existing physical QA holds for both historical count post and historical count rollback, after the branch lock and balance locks and before mutation. Absolute count observations and cost generations remain unchanged.
- A normal positive stock adjustment, including a non-replay stock-count adjustment, is a stock decrease when rolled back. Its rollback must check the resulting locked pile against active QA holds and leave the original adjustment and QA state unchanged if refused.
- Transfer rollback removes stock from the destination pile. For ordinary and WAC/FIFO/Standard historical rollback, acquire the affected pile locks in stock-slice order inside the root transaction, validate current quantities/row versions, restore any original QA allocations, and reject if a resulting pile would fall below its active reservation. Verify failed rollback leaves both piles, value, audit facts, batch status and holds unchanged; verify the exact-reservation boundary succeeds. Transfers must remain value-neutral.
- Historical transfer posting must lock and revalidate both planned piles before checking the source QA hold, so a concurrently placed hold cannot slip between the check and the stock movement. The existing transfer policy still refuses an active source hold.
- Historical MI, Scrap and Vendor Return use the same QA stock-out authorization seam. Lock each tenant-scoped source pile in stock-slice order before reading its on-hand quantity and active holds; the replay writer must still revalidate its prepared plan. Verify a held source blocks an otherwise supported backdated issue, without changing inventory, value or the document, and that the reservation boundary can post and roll back.
- Physical invariants: for each company/branch/item/warehouse/location/lot/status/base-UOM slice, existing stock and active holds must remain distinct; replay may not spend held quantity or reduce stock below a reservation. Each Production pool must retain enough quantity to cover its active logical holds. GR and FG claims must not exceed the accepted source quantity.
- Lifecycle invariants: successful rollback reverses the matching QA allocation once and makes only its accepted quantity available again; repost must not duplicate it. Failed, closed-period, stale, unsupported or injected-failure replay must leave stock, valuation, WIP, PO quantity, QA grants, allocations and hold status unchanged. Preserve same-source ownership and original business audit rows.
- A FIFO backdated MR/GR after a reversed Production issue can proceed when the existing issue used only older verified layers. An active physical QA hold prevents receipt rollback below its reservation; rollback succeeds at the exact reservation boundary. The MR/GR cases passed on SQLite, and the GR case also passed on an isolated SQL Server database (`.replay-test-results/sqlserver-fifo-neutral-qa-gr.trx`). Cost-changing FIFO reallocation for a reversed issue remains blocked.
