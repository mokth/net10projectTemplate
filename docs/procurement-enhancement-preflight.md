## Verified source and contract matrix

All inquiry services below resolve the authenticated company/branch first via `IvInquiryScopeResolver.ResolveAsync`, then require `ACCESS` for the caller-supplied menu code. Queries use the resolved company and branch; a client-supplied `BranchCode` does not expand scope. Existing inquiry pages stamp `AsOfDate` from `ICurrentDateService`, which reads `Company.TimeZoneId` and falls back to `Asia/Kuala_Lumpur`. Service fallbacks use `DateTime.Today`, so new pages must always pass the company-local `AsOfDate`.

| EF/schema conventions | `AppDbContext` exposes explicit DbSets, applies configurations from its assembly, and `SaveChanges` overrides only delegate to base. No shared SaveChanges interceptor was found. Existing menu/data deployment uses guarded, idempotent SQL scripts. | Follow-up requires a new isolated entity/config/DbSet plus a separately deployed, idempotent SQL script. | Menu/permissions | `ErpWeb/Menus/menus.xml` is authoritative; `scripts/init-po-inquiry-menu.sql` is the fresh-database seed and uses `ACCESS` per read-only menu. `PermissionCodes.Add` exists for writes. | New menu nodes and idempotent seed scripts must start inactive/ungranted. ## Conditional feature C decision

**NO-GO.** Source inspection found separate availability surfaces: inventory soft reservations, sales-delivery request reservations, work-order demand allocations, and transaction-specific available-quantity calculations. No single read-only API was verified to reconcile company/branch/warehouse, on-hand, DO/WO demand, reservations, future PO receipts, revised/cancelled PO eligibility, lots and UOM conversion together. The plan’s ten-example reconciliation set was not available. Do not build numeric purchase suggestions until this evidence is produced.
