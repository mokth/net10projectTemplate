# Productionv2 Backdated Replay — SQL Server Benchmark Baseline

> **Review update, 27 November 2026:** Treat the timings below as recorded benchmark observations, not certification of the lock budget. The instrumentation measures a later coordinator lock re-acquisition after the Inventory service has already acquired the transaction-owned branch lock. It therefore does not establish the full lock-hold duration or initial competing-writer wait. The query-plan check also does not reject missing plan XML or a nonclustered index scan. Re-instrument the first acquisition, inspect actual replay SQL and rerun representative workloads before claiming headroom or changing the existing 100-event limit. The WAC public path recorded 228 queries for 10 events and 815 for 100; its per-event query growth remains to be addressed.

## 4. Competing-Writer Contention & Provisional Limit

- **Configured `BranchStockTransactionLock` (`sp_getapplock`) Acquisition Timeout:** `15,000 ms` (retained unchanged; never raised as a workaround).
- **100-Event Concurrent Replay + 3 Concurrent Branch Writers (`WAC-100-CONT` + `WAC-COMPETE`):**
  - Replay succeeded: `True` (the `~416.0 ms` and `696.3 ms` reported spans begin at the later measured re-acquisition; complete lock-hold duration is unverified).
  - All 3 competing writers succeeded in this run with **0 reported timeouts** (`mean writer total = 948.2 ms`). The reported `0.3 ms` maximum measures a subsequent lock re-acquisition, not the initial blocking wait; actual wait and headroom were not measured.
- **Provisional online limit:** Retain the existing **100-event** online affected-tail limit across `CheckSimpleWacTailAsync`, `CheckSimpleFifoInventoryTailAsync`, and dependent routes. The measured paths refused 101-event and 1,000-event cases, but the full lock duration, initial wait and applicability to every dependent route are not certified by these observations.
